Authentication

API key setup, encrypted identifiers, rate limits, and idempotency

Base URL and format

All endpoints on this page are under https://api.kadi-kings.co.ke/api/v1 and speak JSON. Send Accept: application/json on every request: without it, a validation failure redirects (302) instead of returning 422 JSON. Send Content-Type: application/json with a body.

X-API-KEY: your-api-key-here
Accept: application/json
Content-Type: application/json

API Key Authentication

Every endpoint needs an active API key in the X-API-KEY header. A missing, unknown or deactivated key returns:

HTTP/1.1 401 Unauthorized

{"message": "Invalid or missing API key"}

A shop key (issued to a bet shop's system under Bet Shops) works only on the /api/v1/shop/* routes; anywhere else it gets 403 {"message": "A shop API key can only be used on shop routes"}. Every other key works everywhere except those routes. Existing keys are unchanged.

Actions that change money record which key made them (as api_key:{id}), for example in resolved_by, created_by and wallet adjustments.

Encrypted Identifiers

Ids in URL paths ({encryptedIdentifier}) are encrypted with OpenSSL AES-128-CBC (the cipher is set on the server by OPENSSL_METHOD): a random 16-byte IV followed by the ciphertext, URL-safe base64 encoded. Each call produces a different string for the same id; the server decrypts them before the request reaches the endpoint. Use POST /api/v1/encrypt below to build them.

A value that cannot be decrypted returns 400 {"message": "Invalid identifier."}. Customer endpoints match the decrypted value against the customer id or account number, so an encrypted account number works too.

Idempotency

Endpoints tagged Idempotent store their response for 24 hours under an idempotency key and replay it for a repeat of the same request: the same status and body, without running the action again.

  • Send your own Idempotency-Key header (up to 64 characters; longer returns 400): one new key per user action, and the same key when retrying that action after a timeout.
  • Reusing a key with a different body returns 409 {"message": "Idempotency-Key reused with different request body"}.
  • Keys are kept per API key: another integration that happens to send the same key value never gets your response or a 409 because of it.
  • Without a header, the key is made from the API key, endpoint and body. Two identical requests within 24 hours (for example two withdrawals of the same amount for the same customer) are then treated as one: the second gets the first response and nothing happens. Client error responses (4xx) are stored too, so an identical retry of a refused request gets the same refusal for 24 hours; server errors (5xx) are not, so a retry after one runs again. Always send a fresh key for a new action.
Idempotency-Key: 5f0c2b4e-8a1d-4f7e-9c33-1d2e3f4a5b6c

Rate Limits

Limits are per API key: every request made with one key (for example everyone working through GMS) shares that key's budget, and different keys never share one. A request with a missing or unknown key is limited per client IP address. A server-side key can be given a bigger budget with php artisan apikey:rate-limit {key id or name} {1-20}, which multiplies every limit below for that key (the bet shop limits under Shop System are not multiplied). Over the limit returns 429 {"message": "Too Many Attempts."} with a Retry-After header (seconds).

LimiterLimitApplies to
write30/minEndpoints tagged 30/min: most creates and money-moving writes
financial5/minEndpoints tagged 5/min: STK Push, loads, M-Pesa withdrawals, referral withdrawals
stats20/minAll /stats/* and /finance/* reports
callback100/minSafaricom callbacks (not documented here)

Endpoints without a tag have no limit.

Dates, money and statuses

  • Record timestamps (created_at, updated_at) are UTC ISO 8601, e.g. 2026-09-20T07:15:00.000000Z. Fields built for display (e.g. created_at in played-game lists, trans_time) are Nairobi time Y-m-d H:i:s. Newer endpoints return ISO 8601 with the Nairobi offset (+03:00).
  • Money is KES. Amounts stored on a record come back as strings with 2 decimals ("1500.00"); totals and newer endpoints return numbers.
  • Transaction status: 1 pending, 2 completed, 3 failed. Withdrawal disburse: 1 pending, 2 sent to M-Pesa, 3 failed. Deposit status: 0 unmatched, 1 pending, 2 completed, 4 refunded.

DELETE /api/v1/customers/{encryptedIdentifier} Delete a customer ▶
API KeyEncrypted ID
200 OK 404 Not Found 409 Conflict

A soft delete: the customer stops appearing in lookups, searches and lists, but the customer row and their wallet are kept, so their history (ledger, deposits, games, finance reports) still points at them. Payments later made to their account number are kept as unmatched deposits, their referral code stops matching signups and they earn no further referral bonuses. Refused with 409 while the customer holds money or has activity in progress; open lists what is in the way: wallet_balance (not 0, including negative), coin_balance, referral_balance, open_game (a stake in a game that still holds money), open_competition, pending_withdrawal (waiting on M-Pesa), pending_referral_withdrawal, pending_hold, open_dispute, pending_shop_withdrawal (a cash withdrawal at a bet shop not yet collected), or house_wallet (the house customer can never be deleted). To stop a customer without deleting them, set status to 0.

Signup bonus. A player who signs up with a valid promo code (promo_code on POST /customers) and is then reported verified (POST /customers/{id}/verified) gets KES 20 in their main wallet. Both signup and verification must happen before the code expires. The house wallet pays it: with excise duty on, the credit is grossed up to KES 21.05, KES 1.05 is excise owed to KRA and the player keeps KES 20. One bonus per phone number.

Locked until played. The KES 20 can be staked on games, tournaments and jackpots, but it cannot be withdrawn, moved to another wallet or spent on coins until the player has staked that much since the bonus (stakes that were refunded do not count). Money the player deposits is never locked. A withdrawal, wallet transfer or coin purchase that would use locked bonus returns 400 with {"code": "signup_bonus_locked", "locked_amount": 20, "available": 5}.

The promotion is switched on, and optionally capped, on the server (PROMOTIONS_SIGNUP_BONUS_ENABLED, PROMOTIONS_SIGNUP_BONUS_BUDGET_CAP). While it is off, codes are not applied at signup and no bonus is paid. Costs are reported at GET /finance/promotions.

Filing a complaint moves the disputed winnings out of the winner's reach straight away and holds them in dispute escrow until the complaint is closed. How bet shops work. A bet shop is a physical counter where players without M-Pesa or a smartphone pay in cash. It is not a customer and cannot play. Each shop has a prepaid float: the owner buys it by paying the paybill with bill ref SHOP-<shop_no>, and spends it loading players' wallets with the cash they hand over (the owner keeps the cash). While M-Pesa callbacks are not authenticated, those payments are not credited automatically: they land as unmatched deposits carrying the shop in bet_shop, and GMS credits each one with POST /deposits/{id}/shop-float after checking the M-Pesa statement (BET_SHOPS_AUTO_CREDIT_FLOAT turns automatic crediting on later). A float purchase has no excise duty; a cash load does, exactly like an M-Pesa deposit. The shop's system uses its own shop API key (issued below), which only works on the Shop System routes and always acts for that shop. Shop status: active; suspended (its keys are refused, the float is kept); closed (final, only once the float is empty, e.g. by recording a float redemption; its keys are revoked). Only GMS can reverse a load: a shop can never take money back from a player. The game server sends bet_shop_no on POST /game/bets and POST /competition/transactions for play at a shop desktop; those stakes and entries carry bet_shop_id and bet_shop_no (both null for online play) in GET /game/bets and GET /competition/transactions.

What the finance endpoints are

Everything under /api/v1/finance/ reports on money: income, cash flow, what is owed to customers, and where the numbers come from. All endpoints are read-only GET requests except recording and voiding expenses and excise duty remittances. They all need the X-API-KEY header.

Response format

Successful responses use the same envelope as the statistics endpoints. Reports over a range include a meta block; every report includes generated_at.

{
  "success": true,
  "data": {
    "generated_at": "2026-09-20T12:00:00+03:00",
    "meta": {
      "period": {"from": "2026-09-01", "to": "2026-09-20", "group_by": "day", "exclude_test": true},
      "ledger_started_at": "2026-09-01",
      "warnings": []
    }
    /* report fields */
  }
}

Lists add summary (totals over everything the filters match, not just the current page), items and pagination:

"pagination": {"page": 1, "per_page": 50, "total": 132, "last_page": 3}

Money is a number in KES rounded to 2 decimals. Validation errors return 422; see Error Responses.

Dates and time zone

Days are Nairobi days (Africa/Nairobi). A range covers whole days from 00:00 on from to 23:59:59 on to. "Today" ends at Nairobi midnight, not UTC midnight.

Ledger start date and warnings

Revenue, stakes, payouts and balances come from the ledger, which began recording on 2026-09-01. Cash in and cash out come from payment records and cover earlier dates. When a range starts before the ledger began, meta.warnings says which figures are zero before that date.

Escrow releases (game and competition payouts leaving their wallets) were only ledgered from a later date, so the trial balance and escrow checks may not balance before it. The warning appears in meta.warnings too.

Test customers

Reports can leave out test customers listed on the server in FINANCE_TEST_CUSTOMER_IDS. There are none by default, so in production every customer is included. When some are listed, reports leave them out unless you send exclude_test=0. The house wallet is always kept apart from customer wallets, whatever this list says. House cuts cannot always be tied to a player, so the income statement only removes cuts it can link to a test customer or a game a test customer played.

Caching and rate limits

Reports whose range includes today are cached for about 2 minutes, so a figure can lag by that long. Closed ranges and past balance sheets are cached for an hour. The drill-down lists are not cached. Finance GET endpoints share the stats limit of 20 requests per minute; recording or voiding an expense or an excise duty remittance uses the write limit of 30 per minute.

Privacy

Phone numbers are masked in JSON and CSV output, for example 254712345678 becomes 2547****5678. This includes phone-like values inside account references. Customer names are shown; use customer_id to look a customer up elsewhere.

Excise duty of 5% is taken from every plain M-Pesa deposit into a customer wallet (C2B confirmation, STK deposits and POST /deposits). A KES 100 deposit is credited in full, then KES 5.00 is debited as excise_duty, leaving KES 95.00. The duty is rounded half up to the cent and there is no minimum deposit. Response formats

Errors are JSON. Most have a message; newer endpoints also have success: false and sometimes a machine-readable code. A few older endpoints put the message in status or error instead; each endpoint shows its own bodies. Branch on the HTTP status and code, not on message text.

400 Bad Request

The request was understood but refused. The identifier in the path could not be decrypted:

{"message": "Invalid identifier."}

An Idempotency-Key longer than 64 characters:

{"message": "Idempotency-Key must be 64 characters or fewer"}

Business rules, for example:

{"message": "Insufficient balance"}

401 Unauthorized

Missing, unknown or deactivated X-API-KEY:

{"message": "Invalid or missing API key"}

404 Not Found

The record does not exist; each endpoint names it:

{"message": "Customer not found"}

An unknown URL:

{"message": "The route api/v1/customer could not be found."}

405 Method Not Allowed

{"message": "The POST method is not supported for route api/v1/customers/search. Supported methods: GET, HEAD."}

409 Conflict

The same Idempotency-Key was sent with a different body:

{"message": "Idempotency-Key reused with different request body"}

Or the action conflicts with the record's state; these carry a code:

{"success": false, "code": "already_resolved", "message": "Only unmatched deposits can be refunded", "data": {...}}

422 Validation Error

Returned when the request has Accept: application/json. errors lists every failing field:

{
  "message": "The email has already been taken. (and 1 more error)",
  "errors": {
    "email": ["The email has already been taken."],
    "account_no": ["The account no has already been taken."]
  }
}

Some older endpoints catch validation failures and return them as 500 (or, for withdrawals, 422 with the errors in status). Each endpoint says so where it happens.

429 Too Many Requests

Over a rate limit (see Rate Limits). Wait for the number of seconds in the Retry-After header.

{"message": "Too Many Attempts."}

500 Server Error

An unexpected failure. The body does not include details in production:

{"message": "Server Error"}

Endpoints that catch their own errors return their own body (for example {"status": "Error creating Customer"}). Retrying a write is safe with the same Idempotency-Key.
